### 丸めスイッチの設計（合意 2026-09-29）
- **遡及しない**：スイッチの切り替えは切り替え後の打刻にだけ効く。過去月・締め済み（LOCKED）の数字は動かさない。是正は翌月から、が労務の実務。過去の払い漏れ算出は機械処理でなく実打刻から行う
- → 丸めは**現行どおり打刻時に適用して保存**する方式を維持（計算・表示時に移す案は取り下げ）。実打刻 `rawClockIn/Out` は必ず保存
- **スイッチは3つ独立**。同じ丸め処理（`applyRounding`）の中で ①→②→③ の順に評価する
  - ① 定時前打刻 → 定時扱い（既存 `roundEarlyClockIn`）。早出申請がなければ定時出勤とみなす。15分丸めとは別の考え方
  - ② 定時14分以内の早出・残業 → 定時（既存 `roundNearClockTime`）。申請しない限り定時出退勤を促す
  - ③ 全体の15分丸め（新設）。出勤は15分単位で切り上げ、退勤は切り捨て（旧勤怠Reco と同じ）。違法性は高いが実務では通る。法改正で全面禁止になった時に切れるようにするためのスイッチ
- **③ON なら②も強制 ON**（画面ではチェック済みのまま操作不可）。③の切り捨てだけで定時後14分以内の退勤も定時に丸まるため、②OFF が意味をなさない。人間にも挙動が分かりやすい

- **③の15分区切りは本人の定時を起点に刻む**（出勤は始業時刻から、退勤は終業時刻から15分ずつ）。時計の :00/:15/:30/:45 で刻むと、定時が区切りに乗らない人で定時を越えて丸め、架空の早退・遅刻が生まれるため（例：終業17:40・17:43退勤 → 時計刻みだと17:30＝早退10分）。定時が区切りに乗っている人は時計刻みと結果が同じ。**この基準点を忘れると大きなロジックの穴になる** → DOMAIN_MAP.md の丸めの節にも記載済み、実装時はコードコメントとテスト（定時が区切り外のケース）にも残す

### 4. 休憩の記録方式を「打刻」から「申請」へ（合意 2026-09-29・実務担当者ヒアリング結果）
- **実務の実態**：パートは打刻コメント欄に「何時から何時に休憩」と書き、管理者がそれを見て承認・入力している。管理者は再入力の手間がかかっている

- **外出は打刻方式のまま**（予定として事前に準備して打刻できるため）
- **休憩の記録は社員・パートとも休憩申請に一本化**（0分も可）。遅刻早退申請の「休憩0」チェックボックスは作らない。打刻画面の休憩開始・終了ボタンは廃止（過去の休憩打刻データは残す・遡及しない）。控除の判定順：承認済みの休憩申請→申請の分数／申請なし→半休0・パート0＋アラート・社員は規定値（個人の所定休憩→会社設定）
- **打刻画面のUI案（ユーザー提案）**：共通 [出勤][退勤][外出]、パート専用に「休憩時間 [0][15][30][45][60]」のワンタップボタン。申請フォームは汎用的な分入力が煩雑なため、毎日の休憩はボタンで入れる。60分超・入れ忘れは申請フォームで入力
- **休憩ボタンは「その日の休憩の合計」を上書きで設定する**（加算ではない）。押し間違い・1日2回の休憩・休憩前の誤入力は押し直しで直す。加算方式だと押し間違いを戻せないため。案内は「その日の休憩がすべて終わってから押す」
- **申請フォームの時刻入力は自作スピナーにする**（2026-09-29）。時・分それぞれ ▲▼、長押しで連続増減、分は15分刻み、数字の直接入力可（入力欄を離れた時点で15分刻みに補正）。外観は https://copipe-de-ui.net/examples/form-datepicker-2 を参考。初期値は残業申請＝本人の退勤時刻、早出申請＝本人の出勤時刻。ブラウザ標準の `<input type="time">` は iPhone で1分単位のドラムロールになり15分刻みを強制できないため不採用。**利用者アンケートで元のセレクトに戻す可能性がある**（好み・慣れの影響が大きい）→ 部品を1つにまとめ、値の受け渡しを現行セレクトと同じ形にして、差し替え1か所で戻せるようにする。現行のセレクト部品は削除しない
- 訂正：pikaday.dbushell.com は現在ライブラリではなく「日付ピッカーの選び方ガイド」。スクリーンショットの time 入力はブラウザ標準の `<input type="time">`
- **ボタンで入れた休憩は原則承認不要**。出退勤の打刻と同じ「本人の記録」として扱い、管理者は日々の勤怠承認で承認詳細画面から休憩時間もあわせて確認する
- **パートの休憩申請漏れアラートの条件**（2つのどちらかに当てはまる日だけ）：①所定休憩が設定されているのに申請がない ②実働が6時間を超えたのに申請がない。現行の異常検知は「6時間超」しか見ておらず、①（野木さん型）を検知できていない

### 遅刻・早退の時間の定義（2026-09-29 確定）
- **遅刻・早退は時刻の差だけで出す**（今の `calcMetrics` と同じ考え方）。例：所定出勤 9:00・9:23 出勤 → 遅刻23分。所定退勤 15:00・14:12 退勤 → 早退48分。それ以上でもそれ以下でもない
- 一度「働いた時間の不足（所定の労働時間 − 実働）で出す」と合意したが**撤回**。不足の合計は遅刻か早退の理由を推定できるだけで、検算には使えても**新たな時数の算定基準にしてはいけない**（ユーザー指示）
- **原則3（ユーザー指示）**：それぞれの計算式はそれぞれで扱い、ある計算結果を別の新しい値の根拠にしない。計算ロジックの差で謎の数字が生まれ、謎の値ごとにカラムが必要になる
- したがって「遅刻と早退が同じ日にある場合の配分」「休憩を規定より長く取った日の不足（休憩超過）」のような新しい値は作らない。実際の勤務時間は記録に出ているので、それで困らない。管理者に計算上の注意を促すアラートは必要になるかもしれないが、管理者が入力する項目は作らない（入力すべき適切な項目がないため）
- 参考：旧勤怠Reco は 12:05 早退（所定 15:00）を「早 2:00」と出していた（昼休憩分を差し引いた値）。新システムでは時刻の差のとおり
- **【保留・ユーザーが後日精査】③15分丸めON時、遅刻・早退の分数を実打刻から出すか、丸めた後の時刻から出すか**。ユーザーの例（9:23出勤 → 出勤9:30・遅刻23分）は実打刻ベース。旧勤怠Reco（9:29 → 遅 0:30）と現行コード（丸め後の `clockIn` から算出）は丸め後ベース

### 9. 複製で作ったユーザーがアカウント紐づけできない（原因特定・修正は後日まとめて）
- 事象（2026-09-29）：ユーザー管理の「複製」で佐藤さん（会社メール `sato@iwaki-i.com`）を登録 → Google アカウントで紐づけしようとすると「このメールアドレスは登録されていません」
- 原因：`app/link/actions.ts` の `actionFindByCompanyEmail` が、紐づけ済みかどうかを**ログイン用メールアドレスの形で推測**している（`@iwaki-i.com` か `__pending__` で始まる以外は紐づけ済み扱い）。複製（`actionDuplicateUser`）は仮アドレス `duplicate_<時刻>@temp.invalid` を入れ、編集画面では変えられないため、紐づけ済みと誤判定される。新規登録はログイン用メール＝会社メールなので通る
- 本番データ（読み取りで確認）：佐藤さんは1件のみ・仮アドレスのまま・Google 紐づけ0件・勤怠記録0件。余計なユーザーは無し
- 当面の回避策：複製した佐藤さんを削除 → 新規登録で登録し直す → 本人が紐づけ。修正までは複製機能を使わない（ユーザー了承・当面使わない予定）
- 修正方針：①紐づけ済みの判定を「Google アカウントの紐づけ（`Account`）が実際にあるか」に変える（今の判定だと `@iwaki-i.com` 以外の会社メールの人も紐づけできない）②複製ユーザーの編集で会社メールを保存したら、仮アドレスを会社メールに置き換える
